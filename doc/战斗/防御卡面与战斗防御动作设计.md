# 防御卡面与战斗防御动作设计

## 1. 文档状态

- 状态：待确认
- 范围：战斗客户端表现与配套美术资源
- 不包含：战斗数值调整、卡组规则调整、AI 决策调整、数据库结构扩展

## 2. 目标

让玩家和敌人在使用防御卡牌时，画面能够明确表达“正在防御”，不再复用攻击卡面或攻击动作。

完成后应满足：

1. 通用防御卡“防御姿态”拥有独立防御卡面。
2. 男、女玩家角色使用防御卡时播放防御动作，不向敌人冲刺，也不触发敌人受击动作。
3. 敌人使用防御卡时播放对应防御动作，并显示护盾反馈。
4. 敌人使用攻击卡时播放自己的攻击动作；受到伤害、战败和胜利时也使用对应贴图动作。
5. 连续出牌按服务端返回的卡牌顺序逐张播放，攻击和防御动作不能被合并成一次错误动作。

## 3. 当前事实

### 3.1 防御卡面

`BattlePanel.vue` 当前只有两种卡图来源：卡灵牌使用露娜头像，其余卡牌统一使用
`basic-attack.webp`。因此“防御姿态”目前显示为攻击卡面。

### 3.2 玩家动作

现有男、女玩家战斗图均为 4 × 4 帧，包含：

| 行 | 动作 | 帧 |
| --- | --- | --- |
| 1 | attack | 0～3 |
| 2 | hit | 4～7 |
| 3 | death | 8～11 |
| 4 | victory | 12～15 |

当前没有 defense 动作。

### 3.3 敌人动作

当前战斗敌人使用世界地图 NPC 的单张静态贴图。`CardSpirit` 仅在纹理名以 `-combat`
结尾时播放帧动画，因此敌人目前只有通用位移、缩放和闪烁效果，没有独立攻击、防御、受击、
战败或胜利帧动画。

现有需要覆盖的 6 名战斗敌人：

| 敌人 | 当前纹理键 |
| --- | --- |
| 晨曦村村长 | `npc-village-chief` |
| 杂货商 | `npc-shopkeeper` |
| 铁匠少女苏娜 | `npc-suna` |
| 森林向导 | `npc-forest-guide` |
| 训练教官 | `npc-trainer` |
| 狼娘·露娜 | `npc-luna` |

### 3.4 动作触发问题

当前 `battle:action` 事件只描述伤害目标，没有描述出牌者、卡牌类型或动作序列。
防御卡的结算结果也包含 `damage: 0`，因此会被错误地当作攻击动作播放。

## 4. 最小方案

### 4.1 新防御卡面

新增资源：

```text
game-client/public/assets/generated/cards/basic-defense.webp
game-client/art-source/generated/basic-defense-card.png
```

卡面主题：月光护盾、交叠护臂或半透明守护结界，视觉重心朝向角色自身，禁止出现向外劈砍、
飞射物或明显攻击姿态。

视觉要求：

- 延续现有 `basic-attack.webp` 的画风、构图密度和边缘留白。
- 主色使用青绿、银白和少量金色，与攻击卡的暖色冲击感区分。
- 卡图本身不包含卡名、费用、数值或 UI 边框，文字继续由客户端渲染。
- 小尺寸显示时仍能一眼识别为护盾或防御结界。
- 导出 WebP，透明或完整背景形式与现有基础攻击卡保持一致。

首期只对 `type === "defense"` 的通用卡使用该资源。暂不新增数据库卡图字段；未来出现多张
需要独立画面的防御卡时，再引入统一卡图清单，避免为单张卡提前扩展数据模型。

### 4.2 玩家防御动作资源

为现有男女玩家各新增一张独立的 4 帧横向防御动作表，不重做现有 4 × 4 战斗图，避免攻击、
受击、战败和胜利动作发生画风漂移。

```text
game-client/public/assets/generated/sprites/adventurer-female-defense-sheet.png
game-client/public/assets/generated/sprites/adventurer-male-defense-sheet.png
```

动作节奏：

| 帧 | 内容 |
| --- | --- |
| 1 | 收紧重心，双臂或武器回收到身前 |
| 2 | 抬手格挡，护盾能量开始聚集 |
| 3 | 防御姿态稳定，护盾最清晰，作为效果生效帧 |
| 4 | 保持短暂停顿后自然回到待机 |

规格：

- 女角色单帧沿用 313 × 313；整图按 Phaser 实际切帧规则导出。
- 男角色单帧沿用 256 × 256；整图宽度 1024、高度 256。
- 透明 PNG、固定机位、角色中心和脚底基线与现有战斗图一致。
- 动作不得产生明显向敌方位移，角色轮廓在四帧内保持稳定。
- 角色朝向沿用现有战斗场景，由客户端根据左右站位处理，不分别生成左右版本。

### 4.3 敌人战斗动作资源

为 6 名现有战斗敌人分别新增完整战斗动作表。每张图使用 5 行 × 4 帧：

| 行 | 动作 | 目的 |
| --- | --- | --- |
| 1 | attack | 使用攻击牌或签名攻击牌 |
| 2 | defense | 使用防御牌并生成护盾 |
| 3 | hit | 受到实际伤害 |
| 4 | death | 生命归零 |
| 5 | victory | 玩家战败后的敌人胜利动作 |

资源命名：

```text
game-client/public/assets/generated/sprites/npc-village-chief-combat-sheet.png
game-client/public/assets/generated/sprites/npc-shopkeeper-combat-sheet.png
game-client/public/assets/generated/sprites/npc-suna-combat-sheet.png
game-client/public/assets/generated/sprites/npc-forest-guide-combat-sheet.png
game-client/public/assets/generated/sprites/npc-trainer-combat-sheet.png
game-client/public/assets/generated/sprites/npc-luna-combat-sheet.png
```

统一规格：

- 单帧 256 × 256，整图 1024 × 1280，透明 PNG。
- 每行动作 4 帧，角色中心、脚底基线、镜头距离和光源方向必须一致。
- 保留原 NPC 的服装、发型、武器、体型和主色，不把同一角色生成成不同造型。
- attack 可体现职业特点，但命中时间统一落在第 3 帧，方便客户端触发受击反馈。
- defense 必须是原地动作；第 3 帧为护盾效果最强时刻。
- hit 只表达受击，不改变装备或永久姿态。
- death 结尾保持可停留姿势，避免循环。
- victory 克制简短，不遮挡顶部生命条和底部卡牌区。

如果某个敌人动作表缺失或加载失败，客户端必须回退到当前静态贴图加通用 Tween，不能阻塞战斗。

## 5. 动作语义与播放流程

### 5.1 客户端动作事件

将当前只包含伤害目标的事件扩展为按卡牌步骤描述的动作序列：

```ts
type BattleVisualStep = {
  actor: 'player' | 'enemy'
  kind: 'attack' | 'defense'
  damage: number
  blocked: number
  shield: number
  targetDefeated: boolean
}

type BattleVisualSequence = {
  steps: BattleVisualStep[]
  result: 'active' | 'victory' | 'defeat' | 'abandoned'
}
```

规则：

- 玩家单张出牌生成一个 step。
- 敌方连续出牌依据 `last_action.cards` 的原始顺序生成多个 step。
- 卡牌 `type === "defense"` 时 kind 为 defense；其余当前支持卡牌为 attack。
- 不根据 `damage === 0` 推断动作类型，攻击被护盾完全格挡时仍应播放攻击动作。
- 只有 `damage > 0` 或 `blocked > 0` 的攻击步骤才触发目标受击反馈；纯防御不触发受击。

### 5.2 播放顺序

```text
收到新战斗版本
  -> 将公开卡牌结果转换为 visual steps
  -> 锁定下一次出牌操作
  -> 逐步播放
       attack: 出牌者攻击 -> 命中时目标受击/格挡反馈
       defense: 出牌者防御 -> 护盾出现并稳定
  -> 若角色生命归零，播放 death
  -> 若战斗结束，胜者播放 victory
  -> 解锁操作
```

敌人先防御再攻击时，必须先完整播放 defense，再播放 attack。敌人一回合连续使用两张防御牌时，
两次护盾反馈可以连续播放，但不得重复创建永久残留特效。

### 5.3 防御视觉反馈

防御动作由“角色动作 + 短暂护盾特效 + 护盾数值变化”三部分组成：

- 第 1～2 帧进入防御姿态。
- 第 3 帧显示半透明护盾弧或六边形结界，并在此时更新视觉护盾强度。
- 第 4 帧后角色回到待机，护盾特效缩小并保留低强度环光约 400～600ms。
- 护盾颜色：玩家为青绿色；敌人为金橙色或角色主题色。
- `shield === 0` 时仍可播放格挡姿态，但不创建新增护盾数值飘字。

## 6. 代码影响范围

预计修改：

| 文件 | 修改内容 |
| --- | --- |
| `game-client/src/components/BattlePanel.vue` | 防御卡选用独立卡面；按玩家/敌方卡牌结果生成动作序列 |
| `game-client/src/game/events.ts` | 将 `battle:action` 扩展为带 actor、kind 和 steps 的视觉事件 |
| `game-client/src/game/scenes/PreloadScene.ts` | 加载玩家防御表和 6 名敌人战斗动作表，注册 defense 等动画 |
| `game-client/src/game/scenes/BattleScene.ts` | 串行动作队列，区分攻击、防御、受击、战败和胜利 |
| `game-client/src/game/entities/CardSpirit.ts` | 支持独立 defense 纹理、敌人 combat 纹理和防御特效；保留静态回退 |
| `game-client/src/api/types.ts` | 仅在需要严格区分公开卡牌类型时收窄现有类型，不增加服务端字段 |
| `game-client/src/styles.css` | 必要时调整防御卡面裁切和动作播放期间的交互禁用状态 |

不需要修改战斗服务端。现有响应已经提供玩家卡牌 `type/effect`，敌方
`last_action.cards` 也提供 `type/damage/blocked/shield`，足够驱动表现层。

## 7. Must / Defer

### Must

- 一张通用防御卡面。
- 男女玩家防御动作。
- 6 名现有战斗敌人的 attack、defense、hit、death、victory 动作贴图。
- 攻击与防御动作语义分离。
- 敌方连续卡牌动作按顺序播放。
- 缺失动作资源时使用静态回退，不影响战斗结算。

### Defer

- 每张卡牌独立配置卡面字段。
- 不同防御卡拥有不同防御动作。
- 武器、职业或卡灵专属防御特效系统。
- 骨骼动画、实时换装、粒子编辑器和动作状态机框架。
- 音效、震屏、手柄震动和高级镜头演出。
- 未来怪物动作资源；新增怪物时按本规范补充对应 combat sheet。

## 8. 验收标准

### 8.1 卡面

- [ ] 手牌中的“防御姿态”显示独立防御卡面，不再显示 `basic-attack.webp`。
- [ ] 卡面在桌面和移动端均无拉伸、裁切错误或文字遮挡。
- [ ] 攻击牌和防御牌仅看插画即可区分。

### 8.2 玩家动作

- [ ] 男、女角色使用防御牌时播放各自 defense 动作。
- [ ] 防御动作期间角色不向敌人冲刺，敌人不播放 hit。
- [ ] 护盾完全挡住一次攻击时，攻击者仍播放 attack，防守者显示格挡反馈。
- [ ] 玩家攻击、受击、战败和胜利的现有动作不回归。

### 8.3 敌人动作

- [ ] 6 名现有战斗敌人均能加载自己的战斗动作贴图。
- [ ] 敌人使用攻击牌时播放 attack，使用防御牌时播放 defense。
- [ ] 敌人受伤、战败和胜利时分别播放 hit、death、victory。
- [ ] 任一敌人动作资源缺失时回退为静态贴图，战斗仍可继续。

### 8.4 动作序列

- [ ] 敌人连续“防御 -> 攻击”时严格按该顺序播放。
- [ ] 敌人连续多张攻击牌时，每张牌均有独立命中节点，不重复结算数值。
- [ ] 动画只消费服务端已结算结果，不在客户端修改生命、护盾、能量或胜负。
- [ ] 动画播放期间不会因重复点击产生重叠动作或重复 API 请求。
- [ ] 场景退出、投降或战斗结束时，未完成动画队列会被清理。

## 9. 对抗审查

### Launch blocker

1. 不能继续用 `damage === 0` 判断防御，否则被护盾完全格挡的攻击会被误判。
2. 不能让动画回调参与战斗数值结算，否则切后台、掉帧或跳过动画会改变结果。
3. 连续敌方卡牌必须使用服务端返回顺序，不能按类型重新排序。
4. 动画队列必须在场景销毁时取消，避免旧战斗回调作用于新场景。
5. 资源加载失败必须有静态回退，单张坏图不能导致进入战斗失败。

### Follow-up

- 低性能设备可增加“减少战斗动画”设置，但不作为首期阻塞项。
- 后续卡牌数量增加后，再建立卡牌 ID 到独立卡图的资源清单。
- 未来怪物上线前，为其补齐本规范中的 5 组动作。

## 10. 验证计划

1. 运行前端类型检查、构建和 lint。
2. 分别用男女角色测试玩家攻击、防御、受击、胜利和战败。
3. 对 6 名敌人各进行一次战斗，确认 combat sheet 加载和动作方向正确。
4. 构造敌方“纯防御”“纯攻击”“防御后攻击”“攻击被完全格挡”四类回合。
5. 临时移除一张敌人 combat sheet，验证静态回退且控制台无未处理异常。
6. 在桌面和移动视口截图，检查卡面裁切、角色位置、生命条和卡牌区无遮挡。

## 11. 待确认项

本方案默认首期覆盖当前全部 6 名战斗敌人，并为每名敌人一次性制作完整的 5 组动作，而不是
只制作防御动作。这样可以解决敌人目前全面使用静态贴图的问题，也能避免本次新增 defense 后
仍由通用位移动画承担 attack、hit、death 和 victory。

确认本方案后，再进入贴图生成与代码实施阶段。
