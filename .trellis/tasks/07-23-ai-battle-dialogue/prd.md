# AI 对战与对话接入

## Goal

为《斗萝大陆》实现 AI 驱动的 NPC 对话与敌方卡牌战斗决策，使每个战斗 NPC 及后续怪物
拥有自己的卡组，同时保持 FastAPI 服务端对规则、状态、数值和奖励的最终控制。

交付物包括可运行的前后端与数据库改动、自动化测试、配置说明，以及
`doc/AI对战与对话接入设计.md`。

## Background

- 项目是 Vue 3 + TypeScript + Phaser 3 客户端、FastAPI + SQLAlchemy 服务端、
  PostgreSQL 数据库的 Web 游戏 Demo。
- NPC 当前通过 `npc_templates.reward.dialogue` 保存固定对白，客户端
  `DialogModal.vue` 按顺序展示文本。
- 战斗状态由服务端 `active_battles` 持久化；玩家通过出牌和结束回合接口推进战斗。
- 敌方当前不使用模型决策；玩家结束回合后，服务端按 NPC `battle_deck.attack`
  计算一次固定攻击。
- 战斗写操作使用 `battle_id`、玩家归属校验、数据库行锁和
  `expected_version` 保护状态一致性。
- 仓库已具备 OpenAI-compatible 客户端、NPC 对话、有限记忆和单动作敌方 AI；
  本轮需要把敌方固定攻击/防御动作升级为完整卡组与连续出牌序列。

## Requirements

- 文档必须明确 AI 在对话和战斗中的职责边界，区分模型决策与服务端权威规则。
- 服务端必须实现 OpenAI-compatible 客户端、NPC 对话服务、战斗决策服务和确定性降级。
- AI 仅驱动非玩家角色：首期覆盖 NPC，后续怪物复用同一套 AI 能力边界；
  AI 不代替玩家出牌、移动、选择对话或执行其他玩家操作。
- AI 对话采用混合输入：玩家可输入自由文本，也可从两条快捷回复中选择一条发送。
- 两条快捷回复由 AI 根据 NPC 人设、当前对话和可用交互动态生成；模型失败、
  超时或输出不合格时，回退到策划为该 NPC 配置的固定选项。
- NPC 对话需要跨登录、跨设备保持有限记忆。记忆按“玩家 + NPC”隔离，
  保存有上限的近期消息和一段压缩摘要，不保存无限原文，不引入向量数据库。
- 记忆必须有明确的消息条数、摘要长度和保留期限上限，并支持后续清理。
- 自由文本必须设置服务端长度限制、发送频率限制和内容安全检查；客户端限制只作为体验辅助。
- 客户端必须采用 Galgame 式当前台词交互：NPC 当前回复位于场景底部主对白框，
  玩家自由文本和两条快捷回复位于视觉及结构独立的应答区，不把双方历史混排在同一消息框中。
- 客户端仍需提供发送操作，以及加载、失败和降级状态；完整历史继续由服务端作为有限记忆保存。
- 数据库必须持久化按“玩家 + NPC”隔离的有限记忆，并具有唯一约束和清理依据。
- 实现必须覆盖模型超时、限流、返回非法结构、内容安全和服务不可用时的降级行为。
- API 密钥只保存在服务端，客户端不得直接调用模型供应商。
- 模型供应商通过 OpenAI-compatible API 接入，服务端使用环境变量配置
  `AI_BASE_URL`、`AI_API_KEY` 和 `AI_MODEL`，不在业务代码中硬编码供应商。
- 实现必须保持战斗数值结算、卡牌合法性、奖励和最终状态由服务端验证并写入。
- 所有 AI 开关默认关闭；关闭或故障时必须兼容静态对话，并由服务端执行确定性敌方卡牌序列。
- 必须提供不依赖真实外部模型的自动化测试，并保留现有 API 流程测试行为。
- 必须同步完成设计文档、环境变量示例和运行说明。
- MVP 不引入独立微服务、消息队列、向量数据库或长期记忆平台，除非后续需求明确要求。

### AI 角色专属卡组

- 每个可进入战斗且由 AI 控制的角色都必须拥有独立卡组配置；首期覆盖现有战斗 NPC，
  后续怪物复用同一套卡组与回合契约。
- 每个角色卡组至少包含一张角色签名卡，并允许复用普通攻击、防御等通用基础卡；
  不要求卡组中的每张牌都为该角色独占。
- 敌方卡组必须由现有 `card_templates` 中的卡牌组成，不允许模型临时生成卡牌、效果、
  消耗、伤害或其他战斗数值。
- 战斗创建时，服务端必须把敌方角色的专属卡组实例化为独立的抽牌堆、手牌和弃牌堆，
  与玩家卡组完全隔离。
- 敌方必须遵守卡牌消耗、手牌归属、抽牌与弃牌循环；AI 只能从服务端计算出的当前合法
  敌方手牌中选择卡牌。
- 敌方回合允许连续出牌：AI 返回有序卡牌序列，服务端按顺序逐张校验手牌、能量和效果，
  直到能量耗尽或没有可支付卡牌；不满足该“最大可执行序列”的模型输出视为非法并降级。
  模型不得直接决定中间状态或结算数值。
- 模型调用期间不得持有战斗行锁；写入前必须重新加锁、校验 `expected_version`，
  并确认所选卡牌仍在敌方当前手牌且可支付消耗。
- 模型失败、超时或返回非法卡牌时，服务端必须从当前合法手牌中执行确定性降级；
  没有可用卡牌时允许结束敌方回合而不产生伪造动作。
- 客户端必须展示敌方实际使用的卡牌名称、卡牌效果结果和可选角色台词，
  但不得获得隐藏的敌方完整手牌、抽牌顺序或模型提示词。

### 卡灵获取路径

- NPC 卡灵与怪物卡灵使用不同获取路径，不能继续通过注册赠送或一次首胜直接完整获得。
- NPC 采用 1-5 级好感体系：保留 `0-100` 好感值，按每 20 点映射一级，`80-100`
  为好感 5 级；达到 80 点时即可获得对应 NPC 卡灵，100 点保留为满羁绊节点。
- 怪物卡灵通过击败对应怪物获得专属卡灵碎片，不因单次胜利直接加入
  `player_card_spirits`。
- 碎片采用确定性掉落：普通怪物每次胜利掉落 1 枚，精英怪物 2 枚，Boss 3 枚；
  不设置随机区间，重复结算同一场战斗不得重复掉落。
- 每种怪物卡灵的碎片按“玩家 + 卡灵模板”独立累计；集齐 30 枚后才能合成一只完整卡灵。
- 合成必须是服务端原子事务：锁定碎片记录、确认不少于 30、扣除 30 枚，
  再创建唯一的 `PlayerCardSpirit`；重复请求不得重复扣除或重复创建。
- 已拥有完整怪物卡灵后，首期不再允许重复合成；后续多余碎片用途另行设计。
- 战斗奖励响应与卡灵图鉴必须展示本次获得碎片数、当前进度和 `30` 枚合成目标。
- 怪物卡灵的来源角色、签名卡与敌方专属卡组使用同一个 `CardSpiritTemplate`，
  避免战斗角色和可收集卡灵形成两份身份数据。

## Scope

### In Scope

- AI 对话生成的上下文、请求、响应、会话状态与降级策略。
- AI 驱动 NPC 及未来怪物的候选卡牌序列、结构化输出、服务端校验与确定性回退。
- AI 对战只能从服务端根据当前战斗状态计算出的可支付手牌中选择有序序列，可返回角色化战斗台词，
  但不得创建技能、指定未经校验的目标、生成伤害数值或决定奖励。
- 服务端必须忽略模型输出中的额外字段，并逐张重新校验所选卡牌；无效、超时或失败时执行确定性最大序列。
- 服务端配置、安全、日志、成本与延迟控制。
- 客户端需要展示的加载、失败、重试和降级状态。
- 客户端对话框需要提供自由文本输入、发送操作和两条快捷回复，并保留离开与发起对战操作。
- 推荐的接口、数据表或现有 JSON 状态扩展，以及实施和验证步骤。
- 跨会话有限记忆的数据模型、裁剪/摘要时机和读取边界。
- FastAPI 配置、schema、API、服务、数据库迁移与测试。
- Vue/Pinia 对话状态、类型、交互组件和必要样式。
- 设计文档、环境配置示例与 README 使用说明。

### Out of Scope

- 部署或购买生产模型服务，以及提交真实 API 密钥。
- AI 生成或修改战斗规则、奖励、玩家资产和数据库权限。
- 玩家之间的实时 PvP。
- AI 代替玩家操作或双方全自动对战。
- 语音输入输出、图片生成、多 Agent 编排和无限长期记忆。
- 语义向量检索、全局玩家画像和跨 NPC 共享私密对话内容。
- 为未来规模预建微服务、队列、缓存集群或模型路由平台。

- [x] 已领取旧版 NPC 首胜卡牌的玩家迁移后保持已领取状态，不重复获得 1 级奖励。

## Technical Notes

- MVP 对话采用同步 JSON 响应并展示加载状态，不引入流式传输；后续仅在实际延迟体验需要时增加 SSE。
- 现有 `httpx` 和 `pydantic-settings` 足以实现首个 OpenAI-compatible 适配器，
  无需立即增加供应商 SDK。
- 当前 `NpcTemplate` 同时承担 NPC 与战斗敌人配置；未来怪物模型出现时，
  通过服务层的统一 AI 战斗角色契约复用决策逻辑，不提前建立多态平台。
- 首期敌方卡牌效果只覆盖当前服务端可权威结算的伤害与护盾；治疗、抽牌、能量修改、
  Buff/Debuff、召唤和 Boss 改规则等效果留到对应效果引擎任务。
- NPC 好感 MVP 复用现有植物背包与植物基础好感度；非植物礼物、任务解锁、商店折扣和
  角色剧情延后。有效交谈只由成功保存的新聊天轮次触发，重复 `request_id` 不重复增加。
- NPC 首次对战按战斗完成计算，不要求胜利；同一场战斗只在结算时增加一次好感。
- 怪物碎片只在服务端确认胜利且首次完成结算时发放；多余碎片的兑换、升星或返还用途延后。
