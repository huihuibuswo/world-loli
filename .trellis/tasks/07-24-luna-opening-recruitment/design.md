# 技术设计：露娜序章入队与初始卡组调整

## 1. 设计目标

在不引入新框架的前提下，把露娜的受伤遭遇、战败托付、卡灵赠予、返村疗伤和长期主线发布串成完整序章。服务端是奖励与剧情阶段的唯一事实来源；客户端按响应展示战前、战后和返村收尾剧情，并在序章完成后保留“月痕追迹”任务追踪。

## 2. 现有边界

- 注册与初始套牌：`server/app/api/auth.py`
- 战斗结算事务：`server/app/services/battle_service.py::_complete_battle`
- 序章门禁和阶段：`server/app/services/opening_story_service.py`
- 卡灵碎片通用逻辑：`server/app/services/card_spirit_service.py`
- 套牌读写：`server/app/api/decks.py`
- 前端战斗结果：`game-client/src/components/BattlePanel.vue`
- 序章追踪：`game-client/src/components/OpeningStoryPanel.vue`
- 客户端状态刷新：`game-client/src/stores/game.ts`

不新建独立奖励服务层。新增一个职责明确的序章契约奖励函数，由现有战斗结算调用；通用碎片服务只增加“剧情战斗不走普通碎片奖励”的明确门禁。

## 3. 状态与数据流

### 3.1 注册

1. 注册事务创建玩家。
2. 查询“基础攻击”和“防御姿态”模板。
3. 创建 12 张初始库存和启用套牌：6 攻击、6 防御。
4. 缺少任一模板则整个注册事务失败。

### 3.2 露娜挑战

1. `validate_story_battle` 继续要求序章处于 `forest_signal` 且玩家位于微光森林。
2. 失败或 surrender 走现有失败处罚，序章阶段不变。
3. 胜利进入 `_complete_battle` 的同一个事务。
4. 结算识别 `story_gate == opening_moon_scar` 且敌人为露娜后，跳过 `grant_monster_fragments`。
5. 锁定玩家序章进度，确认当前阶段允许首次契约。
6. 发放或复用露娜卡灵，补足月牙撕裂库存和启用套牌数量到 2。
7. 把 `luna_contract_completed`、`luna_injured`、`luna_returning_to_village`、奖励对象和剧情版本写入 `PlayerStoryProgress.data_json`，阶段推进至 `return_village`。
8. 战斗记录、战斗状态与上述奖励一起提交。

### 3.3 客户端

1. 战斗结束响应在 `reward.opening` 中携带契约结果与稳定剧情行。
2. `BattlePanel` 在普通胜利摘要后展示一次契约剧情；重复读取已结算战斗仍可恢复展示，但不会触发服务端再次发奖。
3. 玩家确认剧情并离开战斗后，现有 `leaveBattle()` 刷新 cards、decks、spirits、fragments 和 opening。
4. 序章追踪显示“带露娜返回晨曦村疗伤”。
5. 返村完成接口返回疗伤收尾对白与长期主线对象；客户端展示完收尾剧情后，把追踪器切换为“月痕追迹”。

### 3.4 露娜实体与卡灵语义

- 实体露娜：负伤、被主角带回晨曦村、在序章结束后处于疗养状态。
- 露娜卡灵：实体露娜以月痕凝出的共鸣投影，是玩家收藏与战斗系统中的完整卡灵实例。
- 两者共享人格来源，但卡灵不是把实体露娜收进卡牌，也不意味着实体露娜在赠予后消失。

## 4. 服务端契约

建议扩展 `reward.opening`：

```json
{
  "story_key": "opening_moon_scar",
  "stage": "return_village",
  "event": "luna_contract",
  "message": "露娜主动签订月痕契约，成为你的第一位卡灵。",
  "dialogue": [
    {"speaker": "露娜", "text": "停下……那道月痕还在吞噬我的意识。"},
    {"speaker": "主角", "text": "我的卡组里没有卡灵，但这份力量至少还能替你稳住它。"},
    {"speaker": "露娜", "text": "没有卡灵，却能回应我的月光……原来你不是污染森林的人。"},
    {"speaker": "露娜", "text": "收下我的月痕吧。不是战利品，是我自己的选择。"},
    {"speaker": "露娜", "text": "从现在起，我会成为你的卡灵。下一次，让我们站在同一边。"}
  ],
  "contract_reward": {
    "spirit": {"template_id": 1, "name": "狼娘·露娜", "created": true},
    "card": {"template_id": 2, "name": "月牙撕裂", "count": 2, "added_to_active_deck": true}
  }
}
```

`created` 和 `added_to_active_deck` 表示本次是否实际产生变化，便于兼容补发与测试；它们不控制客户端奖励，服务端持久化结果才是事实。

## 5. 幂等与事务设计

### 5.1 卡灵

- 先按 `(player_id, spirit_template_id)` 查询；不存在时插入。
- 依靠数据库现有唯一约束处理并发竞争。
- 若并发插入冲突，事务应重试或使用 PostgreSQL `ON CONFLICT DO NOTHING` 后重新查询，不能把完整战斗结算误报为 500。

### 5.2 卡牌库存

- 锁定对应 `PlayerCard`；不存在则创建 `count=2`，存在则设为 `max(count, 2)`。
- 不使用 `count += 2`，避免重复结算叠加。
- 复用现有 `(player_id, card_template_id, level)` 唯一约束。

### 5.3 启用套牌

- 锁定玩家的启用套牌；不存在则以可见错误中止整个结算。
- 查找月牙撕裂对应 `DeckCard`；不存在则创建 `amount=2`，存在则设为 `max(amount, 2)`。
- 当前没有总张数限制，标准套牌直接从 12 张扩为 14 张。

### 5.4 序章状态

- 锁定 `PlayerStoryProgress`。
- `data_json.luna_contract_completed == true` 时不得重新发放，只返回已完成契约的响应。
- 只有 `forest_signal -> return_village` 的首次胜利可产生新奖励。
- `return_village` 或 `complete` 的兼容补发只补缺失实体，不重复金币、任务或战斗奖励。

### 5.5 原子边界

`_complete_battle` 当前由上层请求统一提交，因此契约函数只 `flush`，不自行 `commit`。任何模板缺失、约束失败或状态冲突都抛错，让整个结算事务回滚。

## 6. 碎片规则隔离

- `grant_monster_fragments` 的通用掉落规则保持不变。
- 在战斗结算层优先识别露娜序章契约，契约战斗不调用通用碎片发放。
- 不建议把露娜模板全局改成“非怪物”，否则可能影响敌方战斗配置、图鉴或未来非序章遭遇。
- 已存在的露娜碎片保留；拥有完整卡灵后 `can_compose` 继续为 false。

## 7. 剧情展示设计

- 战后契约是胜利结果的一部分，不新增自由跳过后仍需补发的独立服务端阶段。
- UI 使用现有战斗遮罩内的结果区域或轻量剧情页，不创建嵌套卡片。
- 对话逐句前进，最后一页展示卡灵与签名卡奖励，再启用“返回地图”。
- 页面刷新后从已结算战斗的 `reward.opening.dialogue` 恢复，不依赖仅存在于内存的索引之外的数据。
- 无障碍要求：对话区有明确标题，按钮可键盘操作，长文本在移动端换行且不遮挡奖励或离开按钮。
- `complete_opening` 返回 `completion_dialogue` 与结构化 `main_quest`；前端复用轻量剧情面板展示村长接应、露娜安置和主线发布，不只显示 toast。
- 序章完成后 `OpeningStoryPanel` 不应完全隐藏；应切换为紧凑的长期主线追踪状态，显示“月痕追迹”和当前目标。

## 8. 数据迁移与兼容

- 新迁移更新数据库种子/校验，使默认初始套牌目标变为 6 攻击、6 防御。
- 只对完全匹配旧默认组成（6 攻击、4 防御、2 月牙撕裂）的“初始套牌”执行定向修正；自建或已修改套牌不动。
- 对定向修正的旧默认角色，从初始套牌移除月牙撕裂并把防御补到 6。若月牙撕裂库存无法证明仅来自旧默认赠送，则保留库存，但序章奖励仍使用“至少 2 张”语义。
- 对 `return_village` 或 `complete` 且未拥有露娜的角色，执行幂等补发或在显式序章接口中修复；不得借 GET 请求静默提交数据。
- 迁移回滚不删除玩家已经获得的露娜或月牙撕裂，只回滚配置/代码行为，避免破坏玩家资产。

## 9. 失败模式与处理

- 模板缺失：返回 500 配置错误，整笔结算回滚。
- 无启用套牌：返回 409，整笔结算回滚，玩家修复套牌后可重新结算/挑战。
- 并发胜利结算：战斗版本和行锁拒绝重复结算，唯一约束防止重复实体。
- 客户端在奖励后断线：奖励已随战斗结算提交；重新读取战斗可恢复剧情，收藏刷新后状态一致。
- 客户端重复点击：服务端以战斗状态、版本和剧情标记为准，不重复发放。

## 10. 取舍

- 选择在首胜时立即发奖，保证“签订契约”和“奖励到账”是同一事件；返村只负责汇报和序章金币。
- 选择 12 -> 14 张直接扩容，因为当前系统没有套牌上限；不提前引入替牌 UI。
- 选择专用序章函数而非通用奖励 DSL，因为目前只有一个剧情直招例外。
- 选择保留历史碎片而非清零，避免迁移删除玩家资产。

## 11. 回滚

- 代码回滚后，新玩家注册与契约行为恢复旧逻辑，但已经持久化的卡灵和卡牌保留。
- SQL 回滚不得删除玩家资产；只恢复种子期望值和必要配置。
- 若上线后发现平衡问题，优先调整露娜序章专用 HP、能量或牌组配比，不回退玩家已获得奖励。
